# threecat 技术研究与可行性依据

> 本文保留 M0 实施前的研究结论和时间边界。当前实装与实测见 [M0 报告](M0-REPORT.md) 及 [ADR](adr/0001-m0-prototype-findings.md)，不把历史“尚未安装”表述当成当前仓库状态。

> 文档性质：开发规划与技术研究，不是已实现能力清单。  
> 研究截止：2026-11-04（Asia/Shanghai）。  
> 适用项目：threecat，面向全流程 AI 编码的开源、无可视化编辑器、WebGPU-only 编译型游戏引擎。  
> 本次范围：只编写本文件，不实现引擎，不选择未经验证的正式依赖版本。

## 1. 研究结论

threecat 的目标是完整游戏制作能力，而不是渲染示例、特定玩法框架或 AI 原型工具。游戏开发者提供需求，外部 AI 编码工具负责代码、资产接入、运行、检查、修复与交付；引擎研发也由外部 AI 执行。**游戏运行时不包含大模型或 AI 智能体。** NPC 的感知、行为树、状态机与寻路属于普通游戏逻辑。

技术方向确定为：**受约束 TypeScript 定义与逻辑 → 编译检查与中间表示 → 按需内容与代码构建 → 数据导向运行时 → 私有 Three.js WebGPU 渲染后端**。这是候选架构，具体编译边界、存储结构和依赖要由原型决定，不能把“路线 C”解释为任意 TypeScript 自动转 GPU 程序。

截至研究截止日期，可确认 Three.js 提供 WebGPU、TSL 和计算能力；WebGPU 路径追踪也有可核对的上游实现。但是，**动态全路径追踪、交互式多物理模拟及其双向耦合、动态几何的光追加速结构更新，是组合后仍需独立攻关的高风险能力**。已有库不等于完整解决方案。[S01–S09][S12–S16]

项目保留全部首发要求：高质量光栅、混合真实场景光追、动态可交互全路径追踪，以及刚体、布料、绳索、软体和流体。性能实测用于说明负载与成本，不用于静默删减这些能力。**完整能力不等于任意场景、任意模式、无限负载均达到 1080p/60 FPS。**

## 5. Three.js WebGPU-only：失败即失败，防止意外回退

### 5.1 已验证事实

Three.js 官方手册说明 `WebGPURenderer` 默认使用 WebGPU，并可回退 WebGL2；部分旧材质与后处理方式不能直接迁移。[S01]

核对不晚于截止日的源码提交 `3231fc2d0cb2a0f261ff293110bcfb8dbf774350`（提交记录日期 2026-10-30）：默认路径选择 WebGPU backend，并通过 fallback 回调创建 WebGL backend；`forceWebGL` 控制优先使用 WebGL，**将其设为 false 并不会移除默认 fallback**。[S02]

因此，仅检查 `navigator.gpu` 或只传一个配置项，不足以证明 threecat 实际运行于 WebGPU。API 存在、adapter 可申请、device 可创建和渲染器最终使用的后端是不同阶段。[S02][S04]

### 5.2 候选实现

- 固定经验证的 Three.js 版本/提交，渲染后端完全私有。
- 在创建渲染器前完成能力探测，再初始化所需 adapter/device 与引擎能力档案。
- 检查最终实际 backend。初始化失败即返回可定位错误，不建立 WebGL 上下文。
- 优先寻找稳定的上游接入点；若版本没有关闭回退的公开入口，允许引擎研发维护小范围、可复测补丁。构建专用入口仅是待验证选项，不承诺零成本移除整套 WebGL 代码。
- 处理 `device.lost`、验证错误和资源重建；不得在恢复时悄悄换成 WebGL。

这属于架构正确性与诊断，不引入源码加密、防篡改、签名封禁、许可证锁定或用户环境对抗措施。源码公开，生态靠公开 API、文档和常规误用检查维持。

### 5.3 原型与验收

| 场景 | 预期 |
| --- | --- |
| 正常 WebGPU | 提供 adapter 能力、实际渲染 backend、初始化阶段与诊断结果 |
| WebGPU 不存在/adapter 请求失败 | 明确失败，不创建 WebGL 上下文 |
| device 创建或渲染初始化失败 | 明确失败，保留错误阶段，不启动 fallback |
| 运行中设备丢失 | 可诊断、可控恢复或明确终止；不切换后端 |
| 浏览器/Three.js 更新 | 重新执行所有失败分支测试，避免上游默认行为改变 |

故障注入可记录是否请求过 WebGL 上下文，但仅用于测试，不作为拦截使用者的保护机制。

## 6. 编译型 SDK 与受控 GPU 扩展

### 6.1 已验证事实

TSL 支持节点表达、存储缓冲和 compute 相关能力，是实现内部图形/计算后端的候选基础；它不是完整的游戏编译器。[S03] TypeScript Compiler API 可创建 program、访问 AST、执行检查及发射代码；这一事实不意味着任意动态 JavaScript 依赖都能被静态求值。[S25]

### 6.2 候选设计

公开层只暴露 threecat 所有的类型：实体与资源句柄、组件 Schema、系统、材质/后处理图、计算任务、受控缓冲与图像描述。内部可转换为 TSL 和 Three.js 节点，**公开签名、返回值、泛型约束、回调上下文和声明文件都不得引用底层对象类型**。

不提供 `getRenderer()`、`getGPUDevice()`、`getThreeObject()` 或任意底层对象注入口；材质、后处理、GPU 计算应有足够完整的公开表达能力，避免开发者被迫寻找逃生口。首发不以直接粘贴任意 WGSL/GLSL 作为扩展方式。

建议将编译内容拆为：

1. **声明构建**：组件、场景、预制体、资产、UI、动画与时间轴形成有版本的中间表示。
2. **逻辑构建**：玩法系统仍可执行为受控 CPU 代码；声明阶段、读写集合和依赖关系，不承诺自动安全并行。
3. **GPU 图构建**：对类型化图进行验证、资源使用分析、变体生成和底层转换。
4. **内容构建**：形成依赖图、分包、流送清单和可追溯的缓存键。
5. **诊断映射**：从节点、生成代码、资源和运行错误定位到游戏源代码与定义。

声明代码的动态能力需要明确：是可执行的构建期程序、受限静态表达式，还是二者分区。不得无约束执行游戏模块后宣称已得到可重现的静态编译结果。动态资产引用提供显式接口，无法分析时给出诊断，不能遗漏内容。

### 6.3 必须验证的接口边界

- 公开类型扫描不含内部依赖；示例只通过公开入口构建。
- 2D、3D、UI、材质、后处理和 compute 的资源句柄能一致管理生命周期。
- compute 提供缓冲布局、工作组配置、边界检查、同步与资源读写契约；不能只暴露一个“执行计算”的空壳。
- 管线异步准备、热更新失效、GPU 数据回读和同步等待成本可观测。
- 图形编译错误能够回到源位置；AI 无需阅读生成的 Three.js 内部代码才能修复。
- 热更新与冷启动结果一致；状态无法安全迁移时显式重载或重启。

## 7. 光追与全路径追踪：标准现状、上游差异和动态风险

### 7.1 硬件 ray query 的截止日状态

**已验证事实**：WebGPU 现行规范提供通用 GPU 图形与计算能力，不能据此宣称已标准化专用硬件光追接口。[S04] GPUWeb 的 `[wgsl] Add a ray query proposal` PR #11056 于 **2026-10-13** 创建；在本次核查中仍是开放提案，**不是已经合并、普遍交付的 WebGPU 标准能力**。[S05] 更早的 GPUWeb issue #535 也属于追踪讨论，不构成浏览器已支持的证明。[S06]

因此，不能把独立显卡拥有光追单元推导为浏览器标准 API 已可直接使用它。即使某实现存在实验接口，首发基础也不能依赖玩家开启实验开关或使用专用浏览器。

**候选方案**：用标准 WebGPU compute 执行软件 BVH 遍历与采样；未来标准硬件 ray query 成熟后，仅作为内部可选实现。软件光追是真实场景光线求交，但不能宣传成已经使用硬件 RT 单元。

### 7.2 `three-gpu-pathtracer` 必须按 tag 与入口判断

这是最容易发生过时结论的地方。项目名称中的 `gpu` 不代表它从一开始就是 WebGPU，也不能用旧 README 判定所有新版本仍只有 WebGL。

| 核对对象 | 可核对结果 | 对 threecat 的意义 |
| --- | --- | --- |
| `v0.0.23` 固定 README | 明确描述基于 WebGL2，并使用 `WebGLRenderer`、`WebGLPathTracer` [S07] | 不能作为 WebGPU-only 运行后端直接采用 |
| `v0.0.28` 发布记录 | GitHub release 发布于 **2026-11-02 06:35:42 UTC**；tag 提交为 `80d188848fd7ca0ae4c565392d0487d9770d5aa6` [S08] | 是截止日前已有内容，但距离研究日期很近，成熟度与更新风险需独立评估 |
| `v0.0.28` 根入口 `src/index.js` | 仍导出 `WebGLPathTracer` [S09] | 不能只看包版本就默认根入口变成 WebGPU |
| `v0.0.28` 的 `./webgpu` | `package.json` 提供独立导出；对应入口导出 `WebGPUPathTracer`，实现导入 `three/webgpu`、`three/tsl` 及 BVH 的 WebGPU 功能 [S10][S11] | 确有可研究的 WebGPU 实现，必须显式评估正确子路径与依赖组合 |

另核对 `v0.0.25` 的固定 README，已经描述 WebGPU compute，并示例使用 `three-gpu-pathtracer/webgpu`；因此不能错误地把 `v0.0.25` 也归为纯 WebGL 版本。[S07b] 该行只陈述固定 tag 中可见内容，不把本次未完整核对的首次引入日期、合并历程或实际 npm 可获取日期当成已知事实。`v0.0.28` 的截止日前 release 时间和对应提交提供了独立时间锚点。

本次直接核对了固定 tag 的 README、package、根入口、WebGPU 入口及实现，不将浮动 `main` 或某个旧教程当成全项目结论。所述 GitHub release 不自动证明 npm 镜像、离线缓存或某个锁文件已具有同样内容；正式选型还需核对实际分发包与完整依赖图。

**结论**：说“这个项目只有 WebGL”已不准确；说“直接安装就得到成熟的动态 WebGPU 游戏路径追踪”也没有依据。还需锁定 tag、提交、入口、许可证、Three.js 与 BVH 依赖，以及实际可运行内容。[S07–S11]

### 7.3 渐进渲染不等于动态游戏已达标

`v0.0.28` 的实现说明场景在设置时被捕获，后续变动需要对应更新；会使累积失效的变化会重新开始。其源码还区分低分辨率预览、编译阶段与持续采样。[S11] 这些机制证明有更新接口，不证明运动时的噪声、时延、画面完整性或帧率已符合游戏要求。

必须单独验证以下链路：

- 相机、灯光、刚体每帧变化时，真实追踪结果是否持续更新。
- 骨骼、Morph、布料、软体、流体表面、破坏和地形修改如何进入追踪几何。
- 刚体变换更新、形变 refit、拓扑变化 rebuild、流送增删各自的成本与正确性。
- 遮挡变化、镜面反射、透明物、快速运动下的历史样本失效、重投影、拖影和闪烁。
- 是否依靠停止移动后累积、低清预览或光栅画面掩盖动态追踪未完成。
- 峰值内存、加速结构上传、管线编译与多帧延迟，不只记录路径采样耗时。

上游的默认选项不自动成为产品策略。原型可以显式启用预览或低分辨率以研究成本，但正式报告必须标注每帧模式、内部尺寸、样本预算与重建状态，不能记为原生分辨率全路径追踪结果。

### 7.4 threecat 三种正式模式

| 模式 | 目标 | 验收重点 |
| --- | --- | --- |
| 高质量光栅 | 完整物理材质、光照、阴影、环境、透明与后处理 | 动态稳定性、艺术控制、性能与资产一致性 |
| 混合真实光追 | 光栅主视图与真实场景反射、阴影或间接光组合 | 屏幕外几何参与求交；效果来源清晰；动态更新正确 |
| 动态全路径追踪 | 交互玩法中的多反弹光传输；非仅拍照和静态累积 | 移动相机、角色及模拟物体持续更新，结果可观测，噪声与延迟可评估 |

**候选统一方式**：内部维护引擎自己的场景、材质和光照中间表示，再映射至各模式。材质支持矩阵需逐项验证，不能假设任意 TSL 材质自动可由路径追踪器解释。自定义材质图在光栅中的任意顶点或片元逻辑，未必能映射为可采样 BSDF；应定义共同核心、模式专用节点及明确诊断，不做无提示近似。

任意布料、软体和流体表面也是追踪更新范围；不能仅展示刚体移动就验收所有动态能力。路径追踪中透明、体积、毛发等具体覆盖范围还需拆分，不预先宣称全部完成。

### 7.5 降噪与“无运行时模型”边界

上游 WebGPU 入口包含 OIDN 相关适配，不代表 threecat 必须引入它。[S10] 降噪路线尚未选定，可比较非模型的时空方法与专用图像重建组件。本项目不加入运行时大模型、智能体或在线模型服务；专用降噪算法不能被含糊称为游戏智能体，也不能借此隐式引入外部服务。若候选需要权重文件、推理运行时或附加下载，必须明确记录依赖、许可、离线分发、延迟与动态画面质量，另行评估，而非默认随上游全部引入。

## 8. 物理与交互模拟：库能力和耦合能力分开验证

### 8.1 Rapier 的已验证边界

官方 JavaScript 入门资料列出 `@dimforge/rapier2d`、`@dimforge/rapier3d` 及兼容分发方式，说明 WASM 初始化与刚体世界的使用。[S12] 关节与确定性也有独立官方文档。[S13][S14]

不能沿用“Rapier 只能刚体、完全没有软体”的旧结论：官方 **2026-09-25** 的公告介绍 Rapier **Rust v0.36.0** 的软体功能、形变约束与耦合能力。[S15] 但公告同时明确提到 Rust 和 TypeScript 支持，并给出二维绳索、形变网格以及软体—刚体双向耦合示例；不能将其说成只存在于 Rust 核心。[S15] **这仍不等于每个 JS/WASM 分发版本接口相同，更不等于流体和任意跨模块双向耦合已全部解决**。官方当前 JavaScript 手册也列出软体章节，但公告及滚动手册不能用来捏造具体 npm 版本与完整发布历史。本次不指定未经核对的 Rapier JS 正式版本；具体 JS 包的 API、构建内容和发布时点需原型核实。[S12][S15][S16]

官方确定性说明有初始化、版本和操作顺序等前提。[S14] 因此，不能把一个刚体库的确定性推广到整套 GPU 布料、流体、渲染与用户代码；混合系统的回放应有容差、状态检查和快照策略。

### 8.2 候选模块划分

| 模块 | 候选实现方向 | 不能直接假定的部分 |
| --- | --- | --- |
| 2D/3D 刚体 | Rapier JS/WASM；统一引擎接口但分别维护世界 | 2D 与 3D 自然共用碰撞世界；载具和角色全部无需封装 |
| 绳索/布料 | 评估可用形变约束接口，或专用约束求解器 | 关节链或摆动着色器即完整可交互绳索/布料 |
| 软体 | 评估 Rapier 新能力及可控的 CPU/GPU 求解方案 | 核心库功能已全量暴露 JS；表面变形即体积模拟 |
| 流体 | 独立 GPU 粒子/网格方案或开源求解器评估 | 水面材质等于流体；粒子动起来等于稳定流体 |
| 跨模块桥接 | 固定步长、子步、碰撞表示、力/冲量交换与状态同步 | 多个库各自能跑便自动耦合正确 |

这些是候选而非既定算法。不得在没有基准和功能验证时宣称某一单库能覆盖完整需求。

### 8.3 双向耦合单列为高风险

必须区分单向碰撞与双向反馈：布料被刚体推开，不等于布料能对刚体施加合理反作用；流体绕过物体，也不等于浮力、阻力和物体排液已正确。

| 代表性交互 | 至少需要的证据 |
| --- | --- |
| 绳索—刚体 | 牵引和反作用、约束稳定性、锚点与断开后的状态 |
| 布料—角色/刚体 | 动态碰撞、穿透控制、反作用的支持范围与成本 |
| 软体—刚体 | 接触、形变、体积/约束控制及反馈 |
| 流体—刚体 | 排液、浮力/阻力、作用与反作用，不以预设动画代替 |
| 流体—形变体 | 支持范围、双向反馈方案、数值稳定性；未验证不得标为已支持 |
| 模拟—破坏/地形 | 碰撞表示更新、约束失效清理、局部重建 |

首发四类可交互模拟均保留。交互矩阵不能默认所有格子全双向成立，也不能通过不写矩阵而藏起缺口；未解决格子登记风险并提交方案决策，不能自动删项。

### 8.4 CPU/GPU 同步与动态 BVH 是两个独立问题

**候选风险判断**：CPU/WASM 刚体与 GPU 形变/流体若每子步回读全部状态，可能导致流水线等待和昂贵的数据传输。需要比较 CPU 主导、小型反馈缓冲、异步延迟耦合与 GPU 主导方案的稳定性、延迟和成本。不得以“GPU 计算快”代替端到端测量。

模拟完成后，还必须更新可视几何、碰撞代理、导航以及光追加速结构。动态 BVH 能 refit 或 rebuild 的事实，不代表几何拓扑持续变化时质量、时间、内存和调度成本均已解决。[S11][S26]

原型至少分开记录：模拟、耦合、几何生成、碰撞更新、BVH 更新、GPU 上传/回读、实际渲染及总帧时间。只报告求解器耗时不足以验收。

## 9. 资产压缩、动画和动态内容管线

### 9.1 已验证基础

- glTF 是可评估的运行时 3D 资产交换基础，支持网格、材质、皮肤与动画等内容；它不是完整引擎场景、玩法或存档格式。[S17]
- Three.js `GLTFLoader` 文档列出 Draco、Meshopt、KTX2 等接入与扩展支持，需要相应解码或转码配置；不是加载器无条件自动处理所有资产。[S18]
- glTF Transform 提供优化、量化、Meshopt/Draco、纹理处理等工具，是离线管线候选。[S19]
- `KHR_texture_basisu` 描述 KTX2 中 Basis Universal 纹理的 glTF 用法；`EXT_meshopt_compression` 定义缓冲视图压缩，包括可用于动画数据的应用。[S20][S21]
- Three.js 动画播放与混合设施可作底层基础；IK、动作重定向、状态机、过场、物理协同并不会因存在 `AnimationMixer` 自动完成。[S22]

这些在线手册会滚动更新。正式选择格式扩展与工具版本时，要再次核对锁定版本实际支持的子集；本文不把当前全部扩展列表追认为截止日全部可用。

### 9.2 候选资产构建图

`源资产 → 检查与规范化 → 材质/骨骼/动画处理 → LOD 与碰撞代理 → 几何和纹理压缩 → 分块与依赖 → 多模式渲染数据 → 清单与发布资源`。

- 以内容、工具版本、参数和目标能力形成缓存键，记录输入输出依赖。
- 保留源资产，不重复有损压缩；区分下载体积、解码峰值、CPU 内存、GPU 显存与加载时间。
- 纹理按颜色空间和用途处理；法线、透明边缘、HDR、材质通道需分别比较误差。
- 骨骼与 Morph 保留语义；压缩后验证姿态、蒙皮、关键帧、边界与动态 BVH，而不是只比静态模型截图。
- 光栅 LOD、碰撞代理、导航数据、光追几何可以有不同表示，但需记录映射，避免反射、阴影或碰撞与可见几何严重错位。
- 模型解码、纹理转码、WASM/worker 文件必须进入离线分发依赖图；不能暗中依赖 CDN 才能运行构建产物。
- 基础资产提供可玩与验证起点；高质量示范内容另设画质验收，不能用占位方块证明高质量资产管线。

### 9.3 动画与世界系统联动验收

至少覆盖根运动与角色控制、IK 与动态地面、重定向与骨骼差异、Morph 与表情、时间轴与音画同步、动画暂停/跳过/恢复、分块加载后的实体绑定。每种动态几何分别进入光栅、混合与全路径追踪；记录光追更新支持范围。

资产加载、生成、热替换、卸载、再次加载要检查句柄有效性和资源释放。状态快照引用稳定资产标识，不保存底层 GPU 对象。

## 10. Windows 自动化：真实 GPU、可见窗口与可靠证据

### 10.1 已验证事实与适用范围

Chrome 官方自动化文章演示 GPU 测试设置，包含平台特定的开关与后端选择；它不是“所有 Windows 无头进程必然使用独显”的证明。[S23] Playwright 官方资料说明浏览器安装、通道及 headless/headed 差异；安装了浏览器自动化工具也不等于已经获得真实 GPU 测试环境。[S24]

WebGPU 运行涉及安全上下文。开发预览应通过本地 HTTP 服务的可信 localhost 环境，发布通过适当的 HTTPS/安全上下文；不能承诺双击 `file://` 中的 HTML 即可运行所有功能。最终仍是独立 `dist/`，不要求指定托管商。[S04]

### 10.2 候选测试分层

| 层级 | 目的 | 不能证明什么 |
| --- | --- | --- |
| 纯 CPU 测试 | 编译、依赖分析、规则、序列化和非图形逻辑 | WebGPU 渲染质量与显卡性能 |
| 软件 GPU/无头辅助测试 | 某些着色器与错误分支检查，明确标注实际环境 | 主流独显 1080p/60 FPS 达标 |
| Windows headed 真 GPU | 浏览器窗口实际运行，自动输入、查询、截图与采样 | 未测试设备的普遍性能保证 |
| 干净环境 AI 使用测试 | ZIP/目录识别、环境准备、开发、诊断、构建与部署 | 引擎所有玩法均无能力缺口 |

核心画面和性能验收必须包含 **Windows 本地交互桌面会话中的 headed 浏览器及真实硬件 GPU**。可见游戏窗口不是编辑器，自动化操作由工具执行，不要求人手动点击。测试时窗口尺寸、前后台、焦点、遮挡、最小化和电源状态都应记录；避免浏览器节流污染结果。

### 10.3 不允许软件 fallback 冒充达标

测试报告至少记录：

- Windows、CPU、GPU、驱动、浏览器与自动化工具版本；引擎与内容版本。
- 实际 adapter/backend、浏览器 GPU 诊断、设备特性与限制。`adapter.info` 等信息可能因隐私策略不完整，不能只相信某个字符串。
- WebGPU 实际初始化结果、错误、设备丢失、是否存在软件 adapter/后端迹象。
- 启动参数、GPU 加速诊断及测试会话环境；不使用强制 SwiftShader、WARP 等软件路径的结果填入硬件性能验收。
- 若无法确认实际硬件路径，标记“环境未验证/阻塞”，不得按通过处理。辅助软件测试可以保留，但必须分开归档。
- GPU timestamp 若不受设备支持，报告不可用，使用已说明局限的替代测量；不得伪造 GPU 时间。

不能简单根据 renderer 名称、浏览器启动成功、截图出现或平均 FPS 判断真实独显路径。远程桌面、虚拟机和无交互 CI 可能改变图形环境，需要实际检测；这不是禁止这些环境，而是不给未经核对的结果背书。

### 10.4 性能与画质证据

- 原生画布尺寸与内部渲染尺寸都记录；禁止用 CSS 尺寸代替实际像素数。
- 分开记录冷启动、管线准备、预热后稳定段、流送段与长时间运行。
- 报告帧时间分布、卡顿、主线程、GPU 时间（可用时）、加载、回读与资源占用；缺失指标明确缺失。
- 记录渲染模式、光线预算、反弹、累积、降噪、动态分辨率、预览与质量配置。
- 图像使用状态断言、参考图容差、时序视频及外部画面检查共同评估；不能只比较一张静态图。
- 捕获全过程说明内容与场景复杂度；不得把较轻的替代场景标为原目标通过。

这些要求是内部证据规范，不转化成玩家端浏览器白名单或固定硬件门槛。

## 11. M0 高风险技术验证计划

本节与 `DECISIONS.md`、`ARCHITECTURE.md` 的需求保持一致：**M0 用于选择实现方法，不重新投票删除首发能力**。当前尚未安装、运行或验证任何引擎依赖，以下是待执行任务，不是测试通过记录。

### 11.1 四条端到端原型

| 原型 | 最小贯通链路 | 必交证据 |
| --- | --- | --- |
| P1 编译与公开 API | TS 声明/系统/计算图 → 检查 → IR → 内容依赖 → 浏览器运行 → 源位置诊断 | 正常与错误样例、公开类型无底层泄漏、增量结果、动态引用处理、冷启动复验 |
| P2 动态渲染 | 同一场景/材质 → 光栅/混合/全路径追踪 → 相机/刚体/角色/形变/拓扑变化 | backend 证明、动态序列、材质支持矩阵、BVH 成本、质量与性能分项报告 |
| P3 交互模拟 | 刚体与四类形变/流体 → 代表性双向耦合 → 动态渲染 → 查询/快照 | JS/WASM 实际能力、耦合矩阵、稳定性、数据往返、BVH 与总帧成本 |
| P4 外部 AI 闭环 | 干净 ZIP/目录 → 自动准备 → 创建游戏 → 修改 → 运行 → 输入/截图 → 故障修复 → `dist/` | 无人工操作记录、结构化输出、可接续任务、Windows 真 GPU 与部署验证 |

P2/P3 应先使用简单几何定位算法与同步成本，再用具有代表性的高质量资产复验；简单场景通过不是高质量目标验收完成。

### 11.2 可并行与不可并行部分

P1、P2、P3、P4 可分配给不同研发 AI，但先协调最小实体/资源标识、时间、诊断和证据格式。各任务使用独立文件范围；共享接口由主线协调。模拟与渲染各自完成后，还必须安排联合原型，不能用并行任务独立通过代替集成通过。

单个 AI 也能按同一任务依赖顺序执行；不引入运行时 AI 编排平台或必须的协作服务。

### 11.3 M0 结束时的决策包

1. 实际运行的源码 tag/commit、下载来源、校验值与依赖锁定结果。
2. GPU/浏览器环境、场景负载、执行命令和可复测证据位置。
3. 每项候选的已验证能力、失败案例、未覆盖点及许可条件。
4. 自研、封装、上游补丁的边界；公开接口不因实现选择泄漏。
5. 三渲染模式与多物理交互的支持矩阵、成本构成和剩余风险。
6. 正式依赖版本提案、迁移成本和替代方案；通过评审后才升级为选型。
7. 若要求组合不可行，保留证据并提出算法/实施顺序/资源调整建议，不以静默缩减首发需求结案。

完整发布仍需完整能力验收。阶段性原型、实验功能、未完成模块不能冒充正式首发。

## 12. 最大风险与后续研究项

| 风险 | 为什么高 | 下一步证据 |
| --- | --- | --- |
| 动态全路径追踪 | 场景更新、噪声、历史失效与实时预算同时存在；新上游 WebGPU 路线成熟度有限 | 动态相机、角色和形变的连续序列与端到端成本 |

| Windows GPU 自动化 | 成功启动或有画面不保证硬件路径及有效性能数据 | headed 真 GPU 诊断、负载与测试会话证据 |
| 版本与时间误读 | 同名库不同 tag、入口和在线文档可能对应不同后端 | 时间锚点、固定源码和实际分发包交叉核对 |
