> 文档性质：中文规划与验收规范，不是引擎实现或功能交付声明。  
> 规划日期：2026-11-04。  
> 当前状态：M0 原型已通过集成与独立 AI 验收，结果见 `evidence/m0/acceptance.json`；本文 53 项完整首发能力尚未正式逐项验收。以下矩阵保留完整交付要求，原型子集不代表对应 CAP 已完成。  
> 范围：已确认的能力全部属于首发正式范围。分阶段实现不等于移出首发；M0 用于确定算法、约束、负载和可行性，不自动授权删减需求。

需求依据为 [DECISIONS.md](DECISIONS.md)，实现边界参见 [ARCHITECTURE.md](ARCHITECTURE.md)，研发排期参见 [ROADMAP.md](ROADMAP.md)。本文聚焦验收，不替代需求决策。

## 1. 范围、术语与矩阵规则

### 1.1 产品边界

- pelican 面向外部 AI 编码工具。人提出需求与反馈，引擎研发、游戏开发、验证与维护均由外部 AI 执行。游戏运行时不包含大模型或 AI 智能体；NPC 指普通代码实现的游戏行为。
- 编译型 TypeScript SDK，无可视化编辑器。场景、资源引用、UI、材质、计算任务和演出均可通过代码定义。游戏内完整 UI 是正式能力。
- 游戏通过完整公开 API 开发，可定义组件、系统、预制体、材质、后处理和计算任务。公开类型与对象不泄漏 Three.js、TSL、原生 WebGPU 或物理依赖。规范不提供绕过封装的路线，不设计防篡改、账号、授权平台或强制封禁。
- 图形后端优先 WebGPU，允许 Three.js 内置 WebGL2 光栅回退，不主动降画质；compute/混合/路径追踪/降噪在不支持时明确报错并给可用模式。3D、2D、2.5D、光栅、混合真实光追、全路径追踪均属正式范围，不能用屏幕空间近似代替真实场景光线追踪。主里程碑硬件证据仍限定真实 WebGPU；WebGL2 独立实测。
- Windows 是开发环境支持范围。玩家端按实际能力运行，不设操作系统、浏览器或版本白名单。测试设备只承担复现与衡量，不是玩家准入条件。
- GitHub 仓库、ZIP 解压目录、复制目录、外部游戏项目和 npm 安装均是正式入口；共用公开 SDK/CLI/AI 能力，npm 使用不需要引擎源码。不依赖 Git 元数据或固定路径。允许首次联网准备环境；本地依赖与资产齐备后的开发、测试、构建和运行不依赖在线服务。npm 包附许可与版本校验，不含源码映射、证据、示例或游戏资产。
- 不管理或限制资产创作工具。基础资产应足以形成可玩游戏；高质量成品需要高质量外部资产、生成服务产物或自行生成的内容。引擎必须能处理并呈现这些内容。
- 首发为单机引擎；多人联机不在本文正式验收范围。发布输出为可部署到 Web 服务器的 `dist/`，不依赖 pelican 在线服务。

## 2. 统一完成定义与证据契约

每项正式能力必须同时满足以下条件：

1. **接口可用**：公开类型、运行时校验、生命周期、错误语义、版本行为与可执行示例完整；游戏侧不需要修改引擎或调用内部依赖。
2. **成功和失败均验证**：覆盖正常、边界、无效输入、缺失资源、取消、销毁、重复运行与相关的设备丢失恢复。不得靠忽略错误通过测试。
3. **行为有断言**：测试能判定预期状态和事件，画面类能力同时有图像或序列证据；截图只能作为证据之一。
4. **集成有证据**：满足对应 INT 契约和 ACC 场景；单模块演示不代替跨系统验证。
5. **成本有记录**：记录启动、稳态、最坏事件、长时间运行及释放后的相关 CPU、GPU、内存、资源、加载和同步成本。指标不可用时标记原因，不用零值冒充。
6. **可独立复测**：干净环境可按记录重跑；热更新成功不代替冷启动测试；依赖对话记忆或未记录人工操作的步骤不合格。
7. **外部 AI 可用**：无研发历史上下文的游戏开发 AI 能凭交付内容完成典型任务、理解诊断并修复错误。复杂能力需要代表性任务，不能只检查文档是否存在。
8. **交付一致**：文档、类型、示例、构建产物和验收记录对应同一版本；未通过项保持未验收，不用实验标记抵扣正式首发范围。

每次验收证据至少记录：任务编号、源码与内容版本/摘要、依赖锁定信息、测试输入、场景种子、运行模式、实际后端、设备与驱动/浏览器信息、执行步骤、预期与实际结果、阈值来源、原始日志及产物路径。根据任务附上状态轨迹、视频/图像序列、音频、性能采样、快照或回放文件。证据保存在对应项目的可追溯位置，不要求全部大文件进入引擎 Git 仓库。

非确定结果需记录重复次数、误差指标、随机源和通过规则；偶发通过不构成验收。证据自身应可关联版本并验证完整性，不能只留一句通过结论。

### 6.1 物理精度和设备差异

- 固定步长、受控随机源和操作顺序是复现基础，但不承诺所有 GPU/CPU、驱动和浏览器逐位一致。
- 相同受控环境验证可复现程度；不同运行设备使用 M0 锁定的状态误差、接触误差、约束误差、体积/质量偏差及玩法结果容差。
- 容差需与物体尺度、时间窗、求解设置和用途关联；不能用放宽整体容差掩盖穿透、非有限值、失控能量或错误玩法结果。
- CPU 与 GPU 求解、不同子步及异步提交必须记录。双向耦合需测量延迟和稳定性，不能只展示两个物体同时运动。
- 2D 与 3D 物理各自正式支持；二者共处一个游戏的生命周期与事件必须一致，不自动承诺跨维度接触或统一求解。

### 7.1 状态捕获成本与恢复语义

M0-07、CAP-48 必须给每类状态明确以下分类，并通过恢复后的实际行为验证：

| 状态类别 | 规划中的恢复契约 | 不允许的完成替代 |
| --- | --- | --- |
| 游戏逻辑、实体关系、任务与玩家进度 | 精确序列化或显式版本迁移，恢复后符合逻辑断言 | 只恢复位置而丢失任务/引用 |
| 刚体/布料/绳索/软体/流体 | 确定哪些状态精确保存、哪些由检查点重放或容差重建；记录约束及必要内部状态 | 默默清空流体、重置软体或保留明显错误的接触 |
| GPU 缓冲与高密度场 | 比较全量/增量捕获、检查点与重建成本；锁定捕获频率和可支持负载 | 无测量地宣称每帧快照无成本 |
| 音频 | 保存播放意图、轨道/段落、游标/节拍和混音参数；说明流式解码与混响历史的重建策略 | 把没有声音输出的恢复称为音画恢复完成 |
| PT 累积/降噪历史 | 明确失效、重建或保存策略，验证恢复后动态画面稳定；不强求历史缓冲逐字节恢复 | 逻辑恢复后沿用不匹配的历史导致鬼影 |
| 流送、导航重建与异步任务 | 恢复有效请求意图、版本和依赖，取消过期结果，明确恢复就绪条件 | 把旧世界的异步结果写入新状态 |

捕获暂停、异步回读、增量日志和重放各有成本，需记录峰值与持续占用。不得把保存“播放意图”冒充保存所有音频 DSP 内部状态，也不得把容差恢复冒充跨设备逐位确定性。

### 8.2 必须由 M0 明确、不能默认为全部支持的组合

| 编号 | 待决定组合 | M0 必须决定什么 | 首发边界与验证要求 |
| --- | --- | --- | --- |
| INT-17 | 布料↔绳索、布料↔软体、绳索↔软体 | 逐对决定接触/附着/自碰撞及是否双向求解；求解次序和子步 | 不由 INT-01–03 推导六种非刚体组合都已承诺；选定支持的逐项做双侧反应测试，其余明确不支持的交互语义 |
| INT-18 | 布料↔流体、绳索↔流体、软体↔流体 | 逐对决定浮力/阻力/浸润/边界表示的支持等级，双向或单向，以及读回成本 | 不默许完整多相、多尺度统一求解；声明质量/体积误差和负载；核心 INT-04 不能因此取消 |
| INT-19 | 自碰撞、撕裂、断裂与模拟拓扑变化 | 各模拟的自碰撞范围、网格/粒子表示、重建与持久化策略 | 不由物件破坏推导所有模拟任意切割；受支持拓扑变更须通过快照、渲染和光追更新测试 |
| INT-20 | 活跃流体/约束跨流送边界、多个求解器同步 | 选择保留邻区、迁移状态、边界条件或受控暂停；定义恢复和守恒误差 | 不能静默销毁边界状态；支持的跨区方式必须实测，不能声称无限世界里无限活跃模拟 |
| INT-21 | 自定义顶点/计算变形↔物理/导航/光追 | 决定可查询几何、碰撞代理、加速结构输入与同步声明接口 | 装饰性变形可只影响显示但必须显式标记；影响玩法的几何不能只改显示；不能假定任意程序都能自动生成碰撞体 |

以上待决定项的算法、支持表和预算必须落入 ADR 并关联测试；“待决定”不是默认通过，也不能成为取消已确定能力的理由。组合不是所有模块的无限笛卡尔积。确认不支持的非必需组合必须有接口诊断与文档，不应让外部游戏开发 AI 靠猜测发现。

## 9. 画质与性能验收协议

### 9.1 基准与质量分离

已确定的可重复性能基准目标是**主流独显、原生 1920×1080、60 FPS、高质量档**。基准不得依靠动态分辨率或超分辨率达标。具体 GPU/CPU/内存、驱动、浏览器、场景、并发量和通过阈值均尚未锁定，由 M0-05 记录，不能填写假想实测结果。

高画质是独立能力目标，不由 FPS 定义。必须同时验证资产/材质还原、照明、阴影、真实光线效果、动态稳定性、降噪/拖影、细节和透明等。画质参考、误差及序列评估规则同样需要证据来源。

| 测试维度 | 必须固定或记录的条件 | 不允许的替代 |
| --- | --- | --- |
| 光栅、混合 RT、全 PT | 分别标记模式、场景负载、分辨率、反弹/采样/降噪、动态实体和几何更新参数 | 默认所有模式同一负载都保证 60 FPS，或用光栅成绩代表 PT |
| 分辨率与质量 | 输出/内部渲染分辨率、质量配置及运行中变更；基准固定原生分辨率 | 静默降采样、关效果、降模拟密度或切渲染模式 |
| CPU/GPU 时间 | 模拟、调度、提交、GPU 工作和等待分别测量；记录测量能力和开销 | 把 CPU 提交时间当 GPU 完成时间 |
| 帧时间 | 分位数、慢帧、连续卡顿、预热与冷启动分开记录；阈值 M0 锁定 | 只报平均 FPS，删除不利样本 |
| 内容与模拟规模 | 实体、实例、三角形、灯光、模拟粒子/约束、动态几何、流送事件 | 小场景达标即宣称所有游戏达标 |
| 内存与长期运行 | CPU 内存、GPU 资源估算/可用测量、驻留、释放、重复进出和持续运行 | 只测首帧或忽略累积泄漏 |
| 实际 GPU 路径 | 后端身份、适配器、提交与执行；软件/无硬件环境单独标注 | headless 或软件路径通过即宣称主流独显性能达标 |

RT/PT 与重模拟分别建立负载档案；达到何种质量和规模的 60 FPS 承诺必须以测量为依据。测试不达标即保持该项未通过并给出优化/算法任务，不暗降质量。更高分辨率、可选动态质量或超分能力不改变此基准。

### 9.2 玩家端行为

启动由 WebGPURenderer 选择 WebGPU 或内置 WebGL2 回退，并检查游戏实际所需特性和限制。成功则运行，失败给错误码、可用模式及修复操作，不静默降画质。不要求命中官方环境白名单，不把测试配置变成最低硬件锁，也不承诺未经测试设备具有相同性能。
