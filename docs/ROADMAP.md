## 1. 执行原则

1. 当前只编译或构建；高风险行为保持未验证标记，技术可行性不能由文档或编译结果推断。
2. 阶段性可用版本不等于完整首发，不得删掉已确认能力后宣称全部完成。
3. 每个任务必须有输入、前置依赖、写入范围、接口和证据；主线负责集成。单 AI 可以按相同依赖顺序执行。
4. 不预估未经验证的总工期。M0 后根据真实任务数量和风险制定执行批次，不以虚构日期推进。
5. 选型优先采用符合许可要求的成熟组件，但公开 SDK 必须隔离内部依赖。库的存在不代表集成、性能或跨系统一致性已完成。
6. 不建设必需的多 AI 编排平台、资产生成平台或在线控制台；利用现有外部编码工具执行仓库任务。

## 3. M0：必须先完成的风险验证

### M0-00 环境和证据基线

建立最小实验工作区、锁定工具版本、记录 Windows/CPU/GPU/显存/内存/驱动/浏览器。检查 WebGPU 实际可用、实际后端及硬件路径。原生 1080p 的尺寸与浏览器缩放/设备像素比例一起记录。

选定可实际取得的主流独显基线。只有一台机器时如实记录，不据此宣称所有主流显卡达标。补充设备通过后续实测扩展覆盖，不反向形成玩家白名单。

输出：环境清单、可复跑入口、测量方法、证据格式、版本与来源记录。若当前环境没有可用 GPU，仍可推进编译和无 GPU 检查，但不能伪造图形性能结论。

### M0-01 编译链路原型

输入：一个组件、预制体、场景、玩法系统、材质图、资源引用和显式动态引用。

验证：

- TS 检查、声明提取、IR、资源依赖、普通玩法代码构建和运行。
- 非法字段、循环依赖、缺失资源、受控图类型错误映射到原始源码。
- 定义发现不执行任意模块副作用；需要构建期生成时走显式任务。
- 增量变更有缓存失效记录；代码、资源和 Schema 的热更新分别处理。
- 无 Git、带空格/中文路径、外部游戏目录和移动目录后重新定位。
- 运行产物不泄漏开发绝对路径，部署子路径可工作。

输出：编译报告、IR 草案、诊断示例、公开接口草案、构建器候选比较。按当前项目数据评价，不追求一个原型解决所有语言形式。

### M0-02 动态渲染原型

输入：共享场景与材质、运动相机、刚性运动物体、蒙皮角色、Morph/动态形变和一次几何拓扑修改。

验证：

- 明确 WebGPU 后端，初始化失败不转 WebGL。
- 高质量光栅、真实场景射线混合效果、全路径积分三条路径均有可解释画面。
- 加速结构的更新/重建、数据布局、采样和降噪候选方案。
- 动态遮挡、历史失效、重投影、显隐和灯光材质变化。
- 原始采样与降噪结果分别保存；不以强滤波隐藏严重错误。
- 分项记录 CPU、GPU 可得计时、结构更新、显存估计和限制；硬件 RT API 不可用时不冒称调用了 RT 单元。

输出：三模式动态演示和测量、依赖/自研边界、材质支持矩阵草案、风险和明确负载。静态累积图不能通过动态目标。

### M0-03 交互模拟原型

分别评估 2D/3D 刚体底座；再建立刚体与布料、绳索、软体、流体的代表性双向作用场景。比较合适的 CPU/WASM/GPU 分工，记录力和冲量交换、步长、子步、延迟与稳定性。

至少追通：模拟状态 → 几何/变换 → 渲染/光追更新 → 状态查询 → 检查点恢复。高级模块相互作用的优先组合和精度契约在此提出明确矩阵，不使用“未来全部自然兼容”的表述。

输出：求解器候选评估、单位/碰撞/耦合草案、性能分解、状态恢复成本、失稳和资源释放测试。没有稳定实现的部分如实列为风险，不删目标。

### M0-04 外部 AI 开发闭环原型

让一个无研发对话历史的外部开发 AI：读取入口 → 准备环境 → 创建样板 → 修改行为 → 启动浏览器 → 驱动输入 → 查询状态/截图 → 定位故意植入的缺陷 → 修复 → 冷启动复测 → 输出 dist。

拟定工具协议不要求完整生产 CLI，但操作链必须实际可跑。不得由主线在测试过程中临时口头解释隐藏知识。缺失文档和接口作为缺陷修复后重测。

另行进行 ZIP 无 Git 和外部目录项目测试；核对不修改引擎、无底层绕过、无人工操作必要步骤。

输出：任务轨迹、结构化命令结果、修改文件、复测和失败原因、指引改进清单。可用性不能只由研发 AI 自评。

### M0 关联验证项（不新增完整系统交付承诺）

为与能力矩阵中的任务 ID 一致，四条主线另包含以下小规模关联验证：

- **M0-05 基准锁定**：在 M0-00 的环境清单基础上，结合 M0-02/03 实测提出三模式与模拟的负载、阈值和测量契约。
- **M0-06 流送/修改链路**：用最小分块与一次世界修改验证坐标、提交和跨区状态，不要求在 M0 做完整大世界。
- **M0-07 高状态恢复成本**：结合模拟、流送和音频事件验证快照/回放的捕获、恢复和同步成本，不提前承诺长期存档兼容已完成。
- **M0-08 UI 风险预检**：识别中文输入、焦点、世界 UI 的实现风险；专项原型在 M1/M2 完成，完整正式能力归 M6。

### M0 退出评审

四条报告同时提供：已证实、未证实、失败结果、可选替代、成本和下一实验。至少固化以下 ADR：

- 语言/IR/构建器/包管理和工具版本。
- Three.js 版本、后端适配、材质和渲染资源边界；M0 历史 WebGPU-only 结论由当前 D16/D44/D45 的内置回退决策更新。
- 动态光追/PT、加速结构和降噪实现方向。
- ECS、模拟底座、耦合、时钟与状态所有权。
- 基准硬件、测量协议、三模式负载和后续性能门禁。
- AI 操作协议、公开 API 索引、项目发现和路径机制。

若关键组合失败，继续有针对性的原型或向用户提供需求取舍依据。不得通过静默改需求“通过 M0”。

## 4. M1：基础契约与编译运行核心

主要任务：

1. 明确版本化项目/引擎清单、包边界、公开导出和本地路径引用。
2. 建立组件 Schema、句柄、ECS 查询/命令、调度阶段、事件与固定时间服务。
3. 建立定义/系统/图形 IR、来源定位、依赖图和缓存。
4. 建立资源引用、异步加载/取消、共享与释放、失败恢复。
5. 完成诊断结果、运行态检查协议、输入控制、截图与任务状态管理。
6. 统一快照、回放与存档的基础元数据，证明实体与资源身份可恢复。
7. 提供 Windows 自动准备、版本检查和可重复执行入口。

门禁：从简单 TS 场景到浏览器真实执行，能查询实体、改变状态、触发可定位错误、保存/恢复，并在无 Git 外部项目完成相同流程。公开类型不泄漏底层对象；示例仅调用公开 API。

## 5. M2：最小完整游戏切片

制作可玩的小型第三人称关卡：移动/相机、碰撞、动画、一个敌人、交互、任务、物品、UI、音效、保存、离开后恢复。先建立完整闭环，不宣称已覆盖所有正式系统。

同时完成模型/骨骼/纹理/音频导入、基础压缩和优化、原生高质量光栅、可重复输入、冷启动/热更验证以及 dist 部署。素材既要有开箱基础版本，也要有来源清晰的高质量测试资产，不能只用几何体代表真实高质量游戏负载。

门禁：从干净源码目录启动到部署，流程无人工工具操作；外部 AI 可以完成一个新增玩法和一次缺陷修复。性能先记录真实数据，不为达标隐藏工作量。

## 6. M3：高级渲染

本阶段按 D41–D46 增量纳入 npm 编译分发与 WebGL2 光栅回退，先最小端到端再补完整矩阵，不另起阻断 M3 的里程碑。仓库/ZIP/npm 共用公开接口、AI 指引及诊断；主验收继续使用真实 WebGPU，回退独立验证出画面、模式拒绝、生命周期与上下文丢失。性能保留真实负载数据及优化目标，不以僵硬 FPS 阈值延误 1.0；不得降低画质或放松正确性来过关。包发布由 CI 纳入同一已验收提交/标签/Release 节点。

逐步完成混合光追、动态全路径追踪、统一材质/灯光、动态结构、采样/降噪、透明和发光等支持矩阵、模式切换、设备丢失恢复和自定义图形接口。

门禁：移动相机、动画/形变、显隐、世界修改、资源流送与历史重置的专项场景通过；原始与处理后画面、计时、内存、模式配置可审查。各模式的功能、画质和性能分别报告。

## 7. M4：模拟与交互

按 M0 的单位/时钟/耦合协议逐步交付刚体、角色、车辆、关节，再完善布料、绳索、软体、流体、动态碰撞形状和公开查询。与 M3 联合验证形变的加速结构同步。

门禁：能力矩阵所列模块和必需交互均有稳定性、状态恢复、失效处理、释放和多次运行证据。CPU/GPU 数据交换成本计入预算，不能只测单个求解内核。

## 8. M5：世界、导航与动画

完成世界分块、坐标精度、资源预取驻留、程序化生成、构件建造/破坏、地形修改、持久化；完成地面/飞行/水中规划、动态更新、群体和诊断；完善 IK/重定向、形变、代码过场和控制权切换。

门禁：连续世界穿行、修改后离开再返回、路径重规划、过场跳过恢复、光追几何一致性、保存重启等组合场景通过。修改过程中状态未就绪必须可见可处理，不出现隐式不同步。

## 9. M6：多类型开发与完整表现

完成 2D/2.5D、瓦片/精灵/动画、完整 UI、文本/IME、本地化、手柄焦点与可访问性、音频空间/混响/混音/互动音乐。完善可组合玩法模块、可复制模板和文档。

专项游戏建议：2D 平台/动作、俯视建造/管理、对话背包密集界面、物理交互沙盒、连续世界探索。它们是测试负载，规模保持足够验证即可，不把同时制作多款商业成品变成首发前置。

门禁：不同类型不依赖第三人称样板的隐含假设，所有实现都走公开 API。中文输入、字体回退、音频用户手势、世界 UI、音画同步和可访问性有实际浏览器证据。

## 10. M7：性能、升级和发布

在功能稳定后分析真实热点，按证据优化数据布局、批处理、剔除、LOD、分包、驻留、异步任务和管线预热。不能先删除能力再展示速度。

完成版本锁定、升级分析、迁移、恢复测试；检查子路径、资源 MIME、WASM/worker 加载、取消/网络失败、无在线服务启动、许可声明、开发控制通道剔除。

性能协议至少包括：

- 硬件/驱动/浏览器/引擎版本、输出尺寸、实际渲染配置和场景内容量。
- 冷启动与热缓存分别测量；固定脚本、种子、预热和测试时长。
- CPU/GPU 可用计时、帧时间分布、卡顿、加载、内存/资源计数与测量限制。
- 资源反复加载卸载、热更、快照和长时间运行，不以一个瞬间 FPS 作为结论。
- 原生 1080p60 的基准负载与各 RT/PT 负载单列；具体阈值由 M0 实测后固化，不凭空写死。

## 11. M8：独立 AI 使用与首发验收

依照能力矩阵逐项审查，不允许隐藏跳过项。至少完成：

1. ZIP 解压且无 `.git`，干净 Windows 用户环境，从需求到 dist。
2. 本地外部引擎目录，游戏在另一路径，含中文/空格和迁移目录测试。
3. 依赖/资产准备后断网进行日常开发、测试和构建。
4. 无研发上下文的 AI 按文档新增玩法、自定义材质/后处理/计算并修复缺陷。
5. 原第三人称样板加专项场景，验证完整跨系统能力。
6. 版本升级、旧存档迁移、失败恢复和运行态故障诊断。
7. dist 在普通 Web 服务器根路径/子路径运行，无开发控制、账号和引擎服务依赖。
8. 文档、类型、Schema、示例和实装一致；许可/资产来源可审查。

最终报告区分正式通过、实验、未实现、已知问题。存在正式首发必需项未通过时，不宣称完整首发完成。
