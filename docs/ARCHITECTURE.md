# 总体架构与实现边界

状态：研发设计提案，尚未实现。产品要求以 [DECISIONS.md](DECISIONS.md) 为准；本文中的接口名、包名、目录与数据结构为拟定设计，M0 原型后通过 ADR 固化。版本与依赖选择依据见 [RESEARCH.md](RESEARCH.md)。

## 1. 总体结构

```text
外部 AI 编码工具（读取文件 / 执行终端 / 检查画面）
    ├─ 引擎研发：实现、验证、维护 threecat
    └─ 游戏开发：仅使用公开 SDK 编写游戏
                      │
               TypeScript 游戏项目
         ┌────────────┼──────────────┐
      声明定义      玩法系统代码     材质/后处理/计算图
         └────────────┼──────────────┘
                 threecat 编译器
      类型/规则检查 → 多类 IR → 依赖/变体分析
          → 资源构建 / JS 构建 / 管线准备计划
                      │
            版本化清单 + 代码 + 资源分块
                      │
                 threecat 运行时
        ECS / 调度 / 资源 / 事件 / 状态 / 诊断
          ├─ 渲染：光栅 / 混合光追 / 路径追踪
          ├─ 刚体 / 布料 / 绳索 / 软体 / 流体
          ├─ 动画 / 世界 / NPC / UI / 音频 / 玩法
          └─ 内部 Three.js WebGPU / WASM / Web APIs
                      │
                  浏览器游戏
```

外部 AI 不参与每帧运算；开发控制协议是可移除的工具通道。游戏行为由编译后的普通程序、状态机和数值算法执行。

## 2. 公开 SDK 的表达能力

### 2.1 统一概念

| 概念 | 拟定职责 | 关键规则 |
| --- | --- | --- |
| Project / Game | 项目、启动场景、能力与构建配置 | 合理默认值，推导优先，不重复手写依赖清单 |
| Component | 字段类型、默认值、版本、序列化策略 | 有稳定类型 ID；动态状态不混入资源定义 |
| System | 阶段、查询、读写集合、执行函数 | 明确顺序和资源权限；有诊断与性能归属 |
| Entity / Prefab | 实例句柄、可组合定义、覆盖与继承规则 | 实体身份不是内部对象引用；继承冲突可定位 |
| Scene / World / Chunk | 内容、空间和流送组织 | 稳定内容 ID 与运行实体身份分离 |
| Asset | 类型化引用、变体、加载和释放 | 不暴露底层纹理/缓冲；共享所有权明确 |
| Material / Effect / Compute | 受控图与参数接口 | 编译为引擎 IR，不泄露 TSL/WGSL/设备对象 |
| State / Event / Command | 状态、通知和延迟操作 | 约定顺序、生命周期、消费与错误行为 |
| Test / Probe | 输入、状态断言、测量与画面捕获 | 开发测试接口不成为生产游戏必要依赖 |

游戏侧可自由新增组件、规则和系统。限制底层访问是为了让资源、调度、编译和诊断保持一致，不限制游戏题材或玩法类型。具体公开入口设计为 `@threecat/...` 候选，不要求先发布 npm 包；由仓库工具配置本地解析。

### 2.2 三类程序分别处理

1. **内容声明**：组件 Schema、预制体、场景、资源、状态机、时间轴等转换为可验证的数据定义。静态字面量和可分析组合优先；确需生成的内容通过显式、确定的构建任务产生。
2. **玩法逻辑**：受约束 TypeScript 正常编译为 JavaScript；保留函数与模块语义，通过公开查询、命令和服务执行。不尝试全程序证明，也不把任意函数塞进 JSON。
3. **图形计算**：通过引擎提供的类型化节点/表达式构造图，编译为材质、后处理或计算 IR，再由内部适配层生成 TSL/着色器。循环、缓冲访问、资源读写等有明确可校验规则。

三类代码不共用模糊的“所有内容都可静态编译”承诺。需要 IO 的构建任务与内容定义分开；不在扫描项目时随意执行任意游戏模块的副作用。

### 2.3 自定义能力的边界

- 通用 TS 的计算和控制流可以用于玩法系统；需要时间、随机、输入、资源、存储等时通过引擎服务取得。
- 游戏内扩展只能组合公开能力；不提供 `getThreeObject()`、`getGPUDevice()`、任意原生 shader 注入等逃逸接口。
- 建议检查公开包导入、内部路径引用、DOM/图形对象误用及生命周期违规；这些属于开发规则检查，不承诺安全沙箱。
- 高性能批处理通过公开的类型化视图/查询/命令接口提供，既避免每帧对象分配，也不把内部内存布局变成永久 API。
- 扩展点必须有资源声明、生命周期、能力要求、序列化和诊断约定。不能只给一个回调而让使用者自建完整子系统。
- 新扩展需求做成能力缺口报告，由引擎侧决定演进；游戏开发任务不暗改引擎。

### 2.4 建议统一的基础约定

以下为 M0 需要验证并固化的候选，尚不是已实现 API：

- 单位采用米、秒、千克和弧度；2D 明确世界单位与显示像素映射，不隐式混用。
- 世界右手系、Y 向上；相机前向、纹理坐标、2D 屏幕坐标和外部模型转换规则在接口参考中单独说明。
- 颜色输入标记色彩空间，光照运算使用统一线性工作空间；不能让不同渲染模式自行解释同一颜色。
- 数值、向量、矩阵、四元数提供统一类型和零额外分配的批量操作，游戏不依赖 Three.js 数学类。
- 同步调用、异步任务、事件和资源释放分别使用一致返回规范；错误可分类，避免同类方法有时抛异常、有时返回 undefined、有时仅打印日志。
- 可序列化数据与函数、资源句柄、临时查询视图区分；瞬时视图有有效期，不允许跨结构修改后继续持有。
- 公开服务默认配置应可解释，任何自动优化可在报告中追溯；默认值不是隐藏规则。

## 3. 编译器与内容构建

### 3.1 流水线

| 步骤 | 输入与处理 | 输出和错误定位 |
| --- | --- | --- |
| 发现项目 | 项目清单、本地引擎路径、版本/入口 | 项目上下文；不依赖 cwd、Git 或固定盘符 |
| 类型与规则检查 | TS 程序、公开接口索引、导入关系 | 类型结果、规则诊断、源码位置 |
| 提取声明 | 定义调用、Schema、引用与显式生成任务 | 定义 IR；不支持的表达形式明确报错 |
| 建立链接 | 类型/内容/资源/系统依赖和动态引用集合 | 稳定 ID、依赖图、未解析引用报告 |
| 语义检查 | 系统循环依赖、组件字段、材质类型、资源访问 | 有原因的错误，不依赖运行时偶然发现 |
| 构建内容 | 资产转换、场景分块、几何/纹理变体 | 内容寻址资源、来源与工具版本记录 |
| 编译图形 | 材质/计算图、后处理、模式支持矩阵 | 后端中间结果、参数布局、管线准备清单 |
| 构建程序 | 玩法逻辑、运行时模块与服务引用 | JS 分块、source map、模块可达性报告 |
| 打包验证 | 分包、路径、许可与加载清单 | 可部署 `dist/`、可解释报告、版本清单 |

浏览器相关的最终 GPU 管线创建仍发生在实际设备。构建期只能准备代码/描述和预热计划，不能承诺离线生成跨所有 GPU 可复用的机器码。

### 3.2 IR 和单一事实来源

建议内部区分：`DefinitionIR`、`SystemIR`、`MaterialIR`、`ComputeIR`、`SceneIR`、`AssetGraph`、`BuildManifest`。各 IR 有版本、来源位置、依赖和稳定 ID。一个声明更改可以追踪到受影响的产物和诊断。

公开组件/资源/命令定义采用同一元数据源派生类型、Schema、接口参考和索引。复杂 API 可保留手写解释，但签名和示例必须自动验证。具体生成方案通过 M0 验证，不同时维护三份手工 API 真相。

### 3.3 缓存与可重复构建

缓存键包含输入内容、引擎版本、编译器版本、目标能力、选项和转换工具版本；不能仅依赖文件修改时间。输出清单排序稳定，记录必要来源，构建时间戳不污染内容哈希。

动态资产用公开声明指定可选集合或外部 provider；禁止依赖分析失败后默默漏包。无法确定的内容可在报告中明确标记为外部依赖，不强制所有内容静态内置。

### 3.4 增量与热更新

变更传播沿依赖图进行。玩法代码、定义、Schema、材质和资源分别有热更策略。运行时保存状态与新定义默认值不能混合套用；Schema 变化须迁移或重载。更新过程先准备新资源，再在安全提交点切换，失败保留上一可用版本或明确重启。

热更新报告记录输入版本、受影响对象、状态处理、重启情况及失败原因。正式验证始终从冷启动复跑。

## 4. 运行时核心

### 4.1 世界和身份

采用 ECS 为主的统一世界状态。内部内核可封装成熟 ECS 或有限自研，由查询、结构变化、快照等原型决定，公开 SDK 不依赖该选择。

实体句柄包含失效检测信息；持久化内容 ID、跨流送引用与运行时句柄分开。命令缓冲处理创建、销毁、组件结构变化，规定同帧可见性。资源句柄另行管理，不能把实体存活等同于 GPU 资源存活。

### 4.2 调度与时钟

定义固定模拟阶段、展示阶段和异步工作队列。初步阶段：输入采样 → 游戏前置逻辑 → 动画意图/根运动 → 物理与约束 → 后置逻辑/事件 → 导航和世界提交 → 展示姿态 → 渲染。

这只是待验证顺序，IK、物理骨骼、GPU 求解和动画事件需明确分阶段处理，不能用单一回调承担全部前后依赖。各系统声明读写集合、前后约束与执行频率。声明权限有助于诊断，不代表任意 JS 函数可自动多线程化。

控制随机源、模拟 tick 和输入时间；异步资产、音频和外部事件以可记录提交事件接入。渲染插值不改变模拟权威状态。

### 4.3 CPU、Worker、WASM 与 GPU

- CPU：玩法、调度、权威状态、资源/任务管理。
- Worker/WASM：有证据收益的刚体、导航、资产处理等模块。
- GPU compute：图形计算，以及适合的粒子、形变和模拟；不是强制所有物理上 GPU。
- 通过明确数据所有权和交换边界协作，避免主线程逐帧全量读回 GPU。
- SharedArrayBuffer/多线程路径若需要服务器额外响应头，必须报告部署要求；默认静态 `dist/` 仍应提供不依赖这类头的正常执行路径，不能暗中破坏 D38。

### 4.4 生命周期与诊断

资源采用显式所有权/作用域、共享引用和延迟释放。卸载、热更、设备丢失与失败重试必须经过统一路径。开发态追踪实体、系统、资源及 GPU 分配的归属，生产态保留必要错误和能力报告。

GPU 内存和计时数据并非所有平台都可准确取得。报告区分实测、估算和不可用；不把缺少指标写为零成本。

## 5. 渲染架构

### 5.1 公共表示与后端

引擎维护私有渲染场景数据库：几何/实例、材质 IR、灯光、相机、形变结果、可见性和变更标记。ECS 是游戏权威状态，渲染数据库是派生状态，不让游戏直接操作内部 Three.js 场景树。

Three.js WebGPU/TSL 作为内部基础；光追加速结构、路径积分、降噪及与动态模拟的同步很可能需要独立实现或深度适配。不得因为选了 Three.js 就宣称这些已被包含。

初始化必须确认真实 WebGPU 后端。不支持时报告原因，绝不无意回退 WebGL。具体构造方式在锁定 Three.js 版本后验证，不以某个默认参数推断后端身份。

### 5.2 三种模式

| 模式 | 正式职责 | 共同接口 |
| --- | --- | --- |
| 光栅 | 物理材质、光照、阴影、环境、透明、后处理和稳定性 | 场景/材质/灯光/相机/质量配置 |
| 混合真实光追 | 光栅主可见性结合真实场景射线的阴影/反射/间接光 | 加速结构、采样、降噪、调试视图 |
| 全路径追踪 | 动态交互下的多次反弹、发光/透明等材质与累积处理 | 采样预算、反弹、重投影、历史管理 |

模式差异通过支持矩阵公开。自定义材质需定义各模式可执行语义；无法转换的节点在检查时指出，不静默替换为别的效果。屏幕空间反射可作为另一效果，但不能标成真实场景光追。

### 5.3 动态场景关键链路

区分刚性实例变换、蒙皮/Morph、布料/软体形变、流体表面、拓扑变化、地形编辑和流送增删。各类变更标明是否需要 refit、rebuild 或替代表示，并处理包围盒、法线、运动信息和历史失效。

光追结构必须支持几何/实例更新和安全切换。降噪依赖的深度、法线、运动信息与模拟/动画一致。对象显隐、传送、相机切换、材质与灯光变化都需要明确的历史重置策略。

M0 实测动态结构更新、形变、采样降噪和呈现的时间与内存成本。WebGPU compute 软件遍历不等于使用显卡 RT 单元；不将实验特性作为基础运行条件。

### 5.4 质量与性能

质量配置显式列出分辨率、采样、阴影、反弹、降噪、LOD 等。可以由游戏选择自适应策略，但基准测试固定配置并报告实际效果，禁止静默降级。

1080p60 是核心目标；为各模式建立具体负载和质量测试。不能在没有硬件实测时承诺所有模式、任意场景都 60 FPS。高质量资产、材质正确性和画面稳定性独立于帧率评估。

## 6. 物理、形变与耦合

### 6.1 模块组织

2D/3D 刚体、角色、关节和车辆与布料、绳索、软体、流体分别实现或封装专用求解器；通过统一时间、单位、材质、碰撞过滤、句柄和事件语义接入。2D 与 3D 默认是不同物理世界，2.5D 可采用受约束 3D 或 2D，由游戏配置，不宣称两者自动相互碰撞。

GPU 物理选择不能只看单模块速度，还要计入 CPU↔GPU 交换、快照和渲染更新。候选算法需以真实交互和稳定性选择，而非在文档中直接锁定尚未验证的实现。

### 6.2 明确交互，不用演示代替系统

刚体与布料/绳索/软体/流体至少要有代表性的双向作用验证。高级模拟之间的具体耦合契约和组合范围在 M0 明确，最终写入公开支持矩阵；不能暗示所有精度、所有组合无限支持。

力/冲量交换、接触数据所有权、约束求解顺序、子步与延迟必须记录。禁止用“碰到了会动”的单向动画代替要求的交互模拟。

### 6.3 可保存与可调试

定义检查点能恢复哪些状态、哪些需重建；GPU 粒子或网格状态的导出、恢复与耗时单独测量。调试接口能查询约束、接触、能量/稳定性代理指标和求解耗时，避免只观察画面猜测。

## 7. 世界、资源和内容一致性

场景分块、实体持久状态、资产分包和空间导航使用不同索引，不把它们绑成同一文件。资源内容寻址、加载优先级、取消、预取和驻留预算由资源管理器协调。

世界修改采用事务式提交：生成几何 → 物理/导航/渲染准备 → 校验 → 安全切换 → 持久状态记录。对不能同一 tick 完成的更新，提供明确的 pending/ready 状态与可配置交互行为，不留下“看得见但碰不到”的隐性窗口。

大范围坐标采用世界分区/局部原点等候选方案；渲染、物理、音频、导航和存档必须共用坐标转换契约。程序化生成保存种子、生成器版本及用户修改，不只保存最终截图。

## 8. 动画、NPC、UI、音频和玩法

- **动画**：姿态、根运动、IK/重定向、物理骨骼与形变分阶段处理；过场可分支、跳过、恢复，并正确交接控制权。
- **NPC**：感知、记忆、决策与移动规划分离；支持地面、飞行、水中，动态世界修改触发局部更新；每个行为可查询原因与失败状态。
- **UI**：统一代码接口，覆盖屏幕和世界 UI；内部 DOM/canvas 混合或其他路线先验证 IME、文本、焦点、手柄、捕获和性能。底层 DOM 实现不等于给游戏直接开放 DOM。
- **音频**：独立音频时间与模拟/过场建立映射；空间/混响/混音/互动音乐可查询。必须处理浏览器用户手势要求：游戏提供开始交互，自动测试用真实自动化输入触发，不承诺无手势强行有声。
- **玩法**：引擎通用机制与可复制游戏模板分层。背包等模块可以组合、替换规则，示例只使用公开 API。
- **平台服务**：提供必要的输入、用户设置、本地保存、异步资源/provider 和可选 HTTP 能力；不要求构建后端或运行时 AI 服务，不将整个单机能力与远程服务绑定。

## 9. 状态、回放、存档和迁移

划分权威状态、可重建派生状态、外部资源、瞬时显示状态。保存格式引用稳定类型/资源 ID，记录版本、随机源、模拟时间和必要事件。

玩家存档、开发检查点、输入回放分别定义用途和兼容规则：存档注重长期恢复，检查点可保存更详细状态，回放依赖版本与受控事件。GPU 物理和音频等不保证跨机器逐位相同；明确容差与不确定因素。

设备丢失时决定哪些可重建、哪些需从检查点恢复，无法恢复时给出诊断而非继续在坏状态运行。版本迁移以拷贝、验证、提交方式进行，支持无 Git 恢复。

## 10. 拟定目录与项目形态

以下是未来目录，不代表目前已经创建。

```text
threecat/
  AGENTS.md / README.md / LICENSE
  engine.manifest.json       # 名称、版本、公开入口和协议版本
  tools/                     # Windows 启动、环境检查和 CLI 源码
  packages/
    schema/ compiler/ sdk/ runtime/ assets/
    renderer/ physics/ animation/ world/ navigation/
    ui/ audio/ gameplay/ diagnostics/ testkit/
  templates/                 # 可复制修改的游戏模板
  examples/                  # 只调用公开 API 的最小可运行例子
  games/                     # 默认游戏工作区
  tests/                     # 单元、契约、集成、画面、性能、AI 使用测试
  experiments/               # M0 原型，不能作为正式运行时隐式依赖
  docs/                      # 需求、架构、API、ADR、任务与操作指引
  evidence/                  # 可审查证据索引，小型基线与报告
  .threecat/                 # 本地可再生缓存，不是唯一证据存储
```

外部游戏目录包含自己的项目清单、内容、源码、测试与构建配置；明确记录本地引擎位置和版本。工具解析外部路径，不依赖全局 npm link 或导入内部文件。目录搬移后允许重新定位本地引擎，不把机器绝对路径写进发布产物。

未来 `dist/` 至少包括入口 HTML、代码、资产/分块、版本化加载清单和所需第三方声明；开发控制通道默认剔除。使用相对基址或可配置基址，测试根路径和子路径部署；必要的 MIME、HTTPS/安全上下文、跨域等条件由发布检查报告解释，不绑定服务器厂商。

## 11. 初步技术取舍

| 范围 | 候选方法 | 当前决策状态 |
| --- | --- | --- |
| 工作区/依赖 | 固定 Node 版本、单一包管理器和锁文件、仓库命令入口 | M0 选择具体版本；不要求全局安装包管理器 |
| TS/构建 | TypeScript 类型系统与编译 API，现代打包器处理程序与开发服务 | M0 验证提取、增量和 source map，避免无谓自研打包器 |
| ECS | 封装成熟库或有限自研，公开 API 隔离实现 | 依据结构变更、查询、快照测量决定 |
| 渲染 | Three.js WebGPU/TSL + 自有场景/材质/计算 IR | 产品基础已定，具体版本及内部适配待验证 |
| 光追/PT | WebGPU compute、加速结构和降噪，候选现有项目仅供评估 | 高风险原型，不把 WebGL 实现当 WebGPU 成果 |
| 模拟 | 刚体可用 WASM 库；高级模拟与耦合独立评估 | 不宣称单库覆盖全部需求 |
| 内容 | glTF/纹理压缩、网格优化、字体/音频等处理器适配 | 先建立来源和版本记录，再按能力引入 |
| 自动测试 | 浏览器自动化 + 引擎测试协议 + 截图/状态/性能证据 | 验证真实 GPU 路径，不盲信 headless 指标 |

## 12. 不建设的内容

不建设可视化编辑器、运行时模型/智能体、资产生成服务平台、防篡改系统、必需的云控制台或 AI 编排产品。多人联机不进入本次首发。上述边界用于集中实现已确认的完整能力，不限制未来游戏作者的创作和资产选择。
