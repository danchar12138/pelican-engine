## 判断

当前引擎已经具备实际的游戏框架价值：安装和脚手架可用，公开 API 与 JSON CLI 能完成开发闭环，任务、背包、对话、动态 UI、导航、2D 物理和基本三种渲染路径都有运行成功的样本。它不是空实现，也不能仅因若干测试失败就判断所有功能不可用。

但它尚不适合作为可以放心交给另一名 AI 独立交付游戏的稳定基础。普通物理实体出生/销毁、带刚体的区块加载、布料与软体耦合、长时间运行、通过 UI 读档和视口适配都有实测问题。高级功能数量已经领先于集成稳定性。

建议继续开发，但立即把主路径改为稳定性与游戏开发体验收敛。保留代码优先、单一公开 SDK、资源所有权、固定时间步、Three.js 适配和结构化工具等方向；局部重构历史/存档、生命周期、平台呈现和内容生成边界。没有证据支持推倒全部重写，也没有证据支持按当前只编译就继续扩大功能并自动发布的方式前进。

## 已确认的产品问题

P1 表示应先于下一轮功能扩张修复；P2 表示需要安排的产品或体验问题。优先级是本次审查判断，不是新的产品范围决策。

### R01 · P1 · 普通 3D 刚体生成/销毁使游戏故障

公开 API 的独立最小游戏在第一个实际系统 tick（`ctx.time.tick === 1`）执行 `ctx.entities.destroy()` 或 `ctx.entities.spawn()`。两者都编译、启动成功，推进时进入 `TC_RUNTIME_SYSTEM`，底层为 `TC_PHYSICS_OPERATION: 'lifecycle' failed` / `TC_PHYSICS_SNAPSHOT: Invalid history action`。带动态刚体的区块首次加载也失败。

源码直接存在不一致：[历史动作白名单](../../packages/physics/index.ts#L627)未包含 `lifecycle`，而 [bindLifecycle](../../packages/physics/index.ts#L1044)主动记录这种动作；同一 `apply()` 更后面还有对 `lifecycle` 的处理，但前面的白名单使这条路径不可达。不是删掉报错就能证明生命周期完整正确，还需覆盖出生、移除、同 ID 新代、查询、区块停驻和恢复。

影响包括子弹、敌人、可破坏物、物理预制体和动态世界。当前独立回归 `physics-first-removal-regression.ts` 也实际失败；这里不能把失败归因成“Rapier 原有删除陷阱又发生”，因为当前首先失败于引擎自己的动作校验。

证据：`runtime-cases.json` 的 `physical-destroy`、`physical-spawn`、`dynamic-chunk`；`physics-first-removal.log`。三个最小公开游戏保存在证据目录的 `games/`。

### R02 · P1 · 默认布料/软体耦合示例短时间内数值故障

用当前 npm 运行代码，在独立游戏目录复制官方 `cloth-sheet` 和 `softbody-ball` 的 `game.ts`，均编译、启动成功。布料在 tick 18、软体在 tick 2 的 `$engine.physics` 报 `TC_ROPE_BODY_NUMERIC: world inverse inertia diagonal cannot be negative`，调度器标记 `partialState=true`。

涉及的采样入口在 [physics/index.ts](../../packages/physics/index.ts#L1431)，失败检查在 [rope-body-coupling.ts](../../packages/simulation/src/rope-body-coupling.ts#L54)。本次没有隔离到“是哪一笔冲量或原生惯量更新首先不正确”，因此不声称已经证明根因；**默认演示会快速故障**是确定结论。一个无接触的独立原生球体惯量检查正常，也不足以排除耦合路径问题。

建议从子步交换单位、反作用冲量、惯量正定性、数值边界及整体回滚一致性定位。简单取消检查或钳制错误数值，不能当作真实交互已修复。

证据：`runtime-cases.json`。同批 `rope-reaction` 与 `fluid-basin` 推进 60 tick 和快照恢复通过，不能把本问题泛化成四类模拟全部不可用。

### R03 · P1 · 历史记录硬上限让普通长会话停止

[物理历史上限](../../packages/physics/index.ts#L29)是 100,000 条；[每个物理 tick](../../packages/physics/index.ts#L1550)都会追加动作，到上限进入恢复必需状态。浏览器 [默认总是安装 3D 物理插件](../../packages/renderer/src/gameplay.ts#L438)，即便场景没有刚体。

独立进程在空 World 上连续执行当前生产物理系统，准确在完成 100,000 tick 后报 `TC_PHYSICS_HISTORY_LIMIT`。按默认 60 Hz，是 **1,666.67 秒，即 27 分 46.67 秒**模拟时间。其他操作也消耗历史，所以带玩法的会话可能更早。这里是加速执行的模拟时间，不是让浏览器实际等待了 28 分钟。

同一空场景 10,000 tick 的快照 JSON 已约 794,085 字节；本机重放恢复约 71 ms。这不是复杂游戏性能基准，但证明保存内容会随历史增长。存档携带全历史，恢复最近检查点不会给同一时刻的游戏凭空去掉历史成本。

建议把运行状态/存档与调试操作日志分开：周期性建立受版本约束的完整状态基线，日志保留有界窗口；明确检查点与旧 v3 的迁移方案。需要先验证原生恢复可靠性，不能直接把不可信原生字节交给活动 World。

证据：`history-limit.json`；可独立重跑 `node --import tsx evidence/reviews/2026-11-08/reproduce-history-limit.ts`。该探针使用独立物理实例，不在主进程重放危险历史。

### R04 · P1 · 通过实际 UI 按钮读档遗留旧 UI

在官方 `gameplay-loop` 中点击 Accept → Gather → Save → Gather → Gather → Load。逻辑状态正确回到任务 active、1 个水晶，但 `[data-pelican-ui]` 从 1 个变成 2 个，页面同时存在旧的 completed/3 和新的 active/1 状态控件。继续采集、交任务和装备后旧 UI 仍存在。

运行时同时记录 `TC_CONTENT_CLEANUP: previous gameplay: AggregateError: TC_CONTENT_DISPOSE`。使用严格定位器的普通自动化会因同 ID 的两套控件直接失败；即便只操作新 UI，清理错误和遗留 DOM 仍然存在。

源码先 [释放旧 runtime 再释放旧 gameplay](../../packages/renderer/src/browser.ts#L986)；[UI dispose](../../packages/renderer/src/ui.ts#L551)在移除节点/监听器前调用 `reportFocus(null)`，回调抛错会提前退出清理。这组调用顺序和异常路径能够解释实际复现。需要明确切断回调、焦点收尾、Host 销毁和 DOM 释放的顺序，并保证单个回调失败不会跳过其余清理。

证据：`interactions.json` 记录原始严格定位失败；`storage-ui.json` 记录继续操作新 UI 后的持续双根节点和 cleanup 错误；`interaction-gameplay-loop.png` 是继续操作后的截图。该记录中 `assertionsOnCurrentUI=true` 仅表示新 UI 的玩法断言通过，不能用于宣称整个读档流程通过。

### R05 · P1 · 生产画布没有视口适配，高 DPR 也固定为 1

[启动尺寸](../../packages/renderer/src/browser.ts#L66)默认来自 URL 参数或 960×540；[初始化](../../packages/renderer/src/browser.ts#L1732)固定 `setPixelRatio(1)`、`setSize(width,height)`，没有 resize 流程。生产 HTML 隐藏页面溢出。

实际在 1365×768、DPR=2 浏览器里画布仍是 960×540；改成 390×844 后仍是 960×540，图像被裁切。移动尺寸时中央方块已经在可视区域之外。这不是某个玩家平台不受支持，而是同一浏览器窗口尺寸变化就能复现的呈现问题。

建议区分游戏视口、绘制分辨率与离线截图尺寸；运行态根据容器/视口调整相机与渲染目标，并给出明确的质量配置。截图工具可以继续使用固定尺寸。不要用自动降低画质来掩盖适配问题。

证据：`responsive.json`、`production-1365.png`、`production-390.png`。

### R06 · P2 · 失焦处理没有复位键盘按住状态

[onWindowBlur](../../packages/renderer/src/browser.ts#L1507)仅处理 gamepad，并在默认 UI gamepad 模式直接返回；没有清理键盘状态。

测试在正交移动示例按下 ArrowRight 后派发 `blur`，再推进 10 tick，`right` 继续 held，角色 x 从 -3.95 变为约 -3.45；补发 keyup 并推进一 tick 后才释放。**这是合成 blur 事件的处理验证**；本机无头浏览器切换标签没有实际改变 `document.hasFocus()`，所以没有伪称完成真实 Alt-Tab 或操作系统焦点验收。

建议统一处理窗口失焦/页面隐藏/进入文本输入时的键盘释放，并定义恢复焦点语义。证据：`keyboard-blur.json`。

### R07 · P2 · 默认生产页面保留技术 HUD 与引擎标题

生产截图实际显示 `Pelican Engine · raster`、`WebGL2`、三角形数和 tick。它还可能与游戏放在左上角的正常 UI 重叠。来源是 [默认 HTML](../../index.html#L18)和浏览器入口的状态更新，生产时没有关闭。

建议给游戏配置标题/图标/加载与失败界面，并让诊断 HUD 在开发态或显式选项下显示。证据：`production-1365.png` 和 `production-390.png`。

### R08 · P2 · CLI 运行错误丢失最有用的原因

布料、软体和生命周期故障的 `step` 响应只给通用 `TC_RUNTIME_SYSTEM` 与“检查命令和源码”的提示；真正的数值错误或 lifecycle 动作错误要另做 `inspect` 才能看见。对于修复游戏的 AI，这是额外一轮工具调用，也容易误判成游戏源码问题。

建议失败响应直接附带结构化的 tick、system、entity/resource、原始稳定错误码、source 与 cause chain，保留一致 JSON envelope。不要把原始堆栈当唯一诊断。证据：`runtime-cases.json` 中 step 失败及随后 inspect 的差异；原始大快照保留在 `.pelican/review-2026-11-08/`。

## 影响 AI 从零开发的能力缺口与设计成本

以下与上面的实现 bug 分开，不把明确的产品约束伪称为偶发缺陷。

**公开输入缺少鼠标/指针状态。** [InputService / GamepadInputService](../../packages/sdk/src/index.ts#L997)提供动作 held/pressed/released、轴与标准手柄，但没有指针位置、移动量、按钮、滚轮、触摸或 pointer lock 的公开契约。DOM UI 按钮点击已存在，不能代替世界指向、鼠标自由视角和触摸操控。又因为标准游戏代码不能直接操作 DOM/底层对象，另一名 AI 做常见桌面 FPS、拖拽建造或移动端虚拟摇杆时会遇到真实的能力断点。应补引擎管理的平台输入接口，而不是要求游戏修改引擎内部。

**内容声明的 TypeScript 子集成本较高。** 两个类型合法的例子——用 `.map()` 生成实体、用普通函数返回 `defineScene()`——都被 `check` 以 `TC_STATIC_SIDE_EFFECT` 拒绝；定位和建议是清楚的。编译器不执行任意内容函数有合理性，但只建议把行为放到 systems，不能解决大型静态关卡生成。应交付显式、确定性的内容生成入口或更丰富的受限组合器，再考虑是否扩展解释器；不建议直接在扫描期间运行任意游戏代码。证据：`author-friction.json` 和 [extract.ts](../../packages/compiler/src/extract.ts#L481)。

**第三方纯算法库也被当前模块边界一起拒绝。** extractor 只接受公开引擎和项目本地模块，无法直接复用普通 npm 数学/规则等库。禁止泄露 Three.js、TSL、原生物理对象的边界可以保留；普通、可审核的纯 TS 库是否能进入玩法应单独设计，不应自动等同于底层逃逸。当前文档必须把这一限制讲清楚。

**组件数据模型偏窄。** [Field](../../packages/sdk/src/index.ts#L12)只支持 number、boolean、string、vec3。官方 [dynamic-ui](../../examples/dynamic-ui/game.ts#L5)已用 JSON 字符串保存数组，并在更新时 parse/stringify。复杂技能、卡牌、任务条件与自定义结构会重复承担编码、校验和类型成本。可考虑有版本的嵌套 schema/有限数组等受控数据类型，并保持序列化与查询语义一致。

**脚手架与示例距离交付型游戏仍有差距。** 当前跨分发一致的 minimal 模板是旋转方块；完整资产无关配方有 12 个，实际入口是阅读 Markdown 再复制 game.ts。可增加公开 API 编写的 2D/3D 可玩模板，包含输入、相机、胜负/重开、保存、响应式 HUD；生成与编译器一致的项目 TypeScript 配置，并提供能力检索/缺口说明。优先补可靠端到端模板，而不是再增加零散示例数量。

**动态世界与动画仍有明确边界。** STATUS 对共享全局资产缓存、非异步资源流送、没有 origin rebasing、Y-up 运动学贴地而非 ragdoll balance 都有说明。这些是当前范围边界，本次没有把它们当作实现已出错，也没有验收完整大世界或全身动画矩阵。对于另一名 AI，需要在开始游戏时就能按玩法需求发现这些边界。

## 与直接使用 Three.js 的比较

本次没有做同一场景、同一资产、同一曝光/材质和渲染分辨率下的盲测或帧时 A/B。因此不下“Pelican 画质一定更差”“Three.js 一定更快”或具体性能倍数的结论。

| 任务 | 当前判断 | 依据与限制 |
| --- | --- | --- |
| 短期视觉原型、自定义图形效果、鼠标交互强的 3D 展示 | 倾向直接 Three.js 更方便 | Pelican 有额外内容子集、公开能力缺口与已有集成 bug；Three 原始对象与生态能力不需要经过本引擎再暴露 |
| 常规任务、背包、对话、存档协议、固定时间玩法、AI 自动检查 | Pelican 有价值 | 公开服务和工具已能工作；直接 Three.js 时作者还要组织相应游戏框架和依赖，不能把 Three 本身等同于完整游戏引擎 |
| 长期可交付游戏 | 当前 Pelican 稳定性不足，需要先收敛 | 普通实体生命周期、会话上限、存读档清理和视口问题会进入正常玩法 |
| 默认光栅视觉 | 没有证明必然低于原生 Three | 引擎本身使用 Three.js WebGPURenderer；真正差异还取决于公开材质/灯光/后处理覆盖、参数和艺术资产 |
| 混合/路径追踪 | 有真实实现与本机成功样本，仍不能承诺整体优于其他实现 | 最小场景与数值专项通过；完整动态场景画质、降噪时间一致性、复杂资产、负载和跨设备还没有本次对照证据 |

这里的“更方便”是根据本次公开 API 任务和代码审查做出的工程判断，不是一次新的、没有研发上下文的独立 AI 竞赛。当前执行者读过引擎源码；如果要量化“另一名 AI 从零”的优势，应让独立实例只得到已安装的包、目标游戏说明、相同时间预算和相同资产，再记录完成率、修复次数、引擎缺口数与最终游戏表现。

## 架构与继续开发建议

**应保留的方向：** 单包与单一公开 API、游戏/引擎职责边界、代际实体身份、固定步调度、资源所有权、JSON 工具协议、静态部署，以及通过成熟库实现图形/物理的基本分工。此次安装、示例和 GPU 成功样本为这些方向提供了一部分实际支持。

**需要优先调整的局部：**

1. 运行状态、持久存档和调试回放日志分层。先消除固定会话寿命，建立可验证的检查点/版本迁移，不让所有用户承担无限增长的历史。
2. 建立明确的内容切换事务与销毁顺序。UI、音频、模型、物理、Host、GPU 资源的依赖应表达为协议；失败清理必须尝试剩余步骤。当前故障说明“每层都有 dispose”还不等于跨层正确。
3. 平台层负责视口、DPR、输入焦点与指针/触摸；游戏只拿受控公开状态。不要把这些基础能力散落在巨大的浏览器启动入口。
4. 把可选插件依赖与调度契约显式化。当前物理系统对 `$engine.cinematics` / `$engine.models` 的硬编码顺序，与只加载物理插件的旧 Host 测试冲突；必须分清合法最小组合、必要依赖和缺省系统。不能通过无条件塞入空系统掩盖依赖。
5. 内容编译器应服务于规模化内容组织。交付确定性生成路径和更完整的数据 schema，控制自定义 TS 解释器的增长。
6. 为 AI 提供任务可用性索引：给出“可以直接做、需要额外实现、当前受阻”的玩法入口，并使实际包内配方、类型、错误码和示例同步。

**继续推进的建议顺序：**

- 第一批修 R01、R03、R04、R05；同时定位 R02，并为每个实际故障保留最小回归。不要只把报错保护移除。
- 整理 94 个失败断言和 9 个跳过项。旧 harness 缺 `dynamicVisualRevision` 等新全局、旧物理测试只执行 `plugin.systems[0]`、旧 UI 测试服务器未提供新增导入、伪 GLB 被正式解析器拒绝，以及发布测试仍检查废弃的凭证/流程，均需要按实际契约修复。禁止只把失败断言删掉来“变绿”。
- 在用户确认后撤销长期“只编译”的发布推进条件，恢复与改动相称的 CPU/游戏闭环测试，GPU 专项使用明确的环境/能力说明。当前这次授权没有自动修改该长期决策。
- 在统一主线串行方式下做一个交付型 3D 切片：移动/鼠标相机 → 碰撞/物理生成销毁 → UI/背包/任务 → 胜负重开 → 按钮存读档 → 窗口变化 → 超过 28 分钟的模拟时间。完整链路稳定后，再用独立 AI 重做同一任务。
- 对高级模拟、动态世界和全身动画分别建立跨系统场景矩阵，再扩大能力或宣称完整验收。实现勾选、编译通过、最小示例通过和发布到 registry 应使用不同状态。

## 测试失败怎样解读

94 个失败不是 94 个独立引擎 bug。失败索引涉及 18 个测试文件，包含三类：已经通过独立公开游戏再次确认的真实问题、旧断言/测试夹具与当前实现不一致，以及本次尚未单独隔离的回归。`failure-index.json` 提取了报告器输出的 92 个详细失败块，保留名称、位置、错误和完整段落；运行器总失败节点计数为 94，两者分开记录，没有补造缺少的详细段落。

本报告没有逐项修复这 94 个断言，也没有将所有未隔离项判成“只是测试问题”。尤其不能因为一些测试陈旧，就忽视已经在真实公开 API 链路复现的生命周期、数值、读档和视口故障。

当前 GitHub Actions 构建/发布流程只执行构建和打包，符合先前 D50，但这些已复现的运行故障仍可以随构建成功的版本进入 registry。继续研发需要调整的是这个风险接受方式和相关局部架构，不是再用更大的版本号代替运行证据。

未完成的本次审查边界包括：多显卡/多玩家设备矩阵、完整移动触摸、音频设备实际听感、海量资产与世界负载、全身 IK/重定向/过场所有组合、长时间真实浏览器内存趋势、同场景原生 Three.js 画质/性能 A/B，以及无引擎研发上下文的独立 AI 盲测。报告中的通过不外推到这些项目。
